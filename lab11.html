    検索アルゴリズムとデータ構造

    実施日2027年1月12日（火）
    レポートレポート⑤　1/19（火）9:00 締切
    この回でやること名前のデータを線形リストと木構造に入れ、先頭・最終・任意の要素を探す時間を測る。幅優先探索と深さ優先探索の違いと、データの大きさによる変化を確かめる。

    配布資料

    スライド、名前のデータ（2種類）、サンプルコード（TreeMaking）はLMSから取得してください（スライドの日付は1月13日ですが、予定表では1月12日です）。このページは、その内容を自分用に解説したものです。

    手順の一覧

      この解説の使い方

      • 同じ名前のデータを「線形リスト」と「木構造」に入れて、探すのにかかる時間を比べる回です。データ構造によって探索の速さがどう変わるかを、実際に測って確かめます。
      • レポート⑤の対象です。ここでは考え方、時間の測り方、ヒントまでを書き、課題のプログラムそのものは書いていません。
      Javaのコード（書き方の例）

      今回の課題

      スライド「本日の課題」「発展課題」より。

      区分内容手順
      課題1名前のデータを線形リストに保存し、「ア」「カ」で始まる要素の数を数える2
      課題1先頭・最終・任意の要素の3つについて、検索時間を測る。大きさの違う2種類のデータで比べる3〜4
      課題2名前の文字をキーにした木構造を作り、幅優先探索と深さ優先探索で検索して、時間をまとめる5〜7
      発展ハッシュでの探索時間／バランスをとりながら木を作る方法／最長しりとり8
      1

      先に、計算量の見通しを持つ

      スライド「データの探索と計算量」
      データ構造探し方計算量特徴
      線形リスト先頭から順に比べる（線形探索）O(N)作るのは簡単。途中への挿入などは負荷が大きい
      二分木（均衡）大小で左右に進むO(log N)速いが、バランスのよい木を作るのが難しい
      ハッシュ値から置き場所を計算して直接見るO(1)発展課題

      O(N) は「データが2倍になると、時間もおよそ2倍」という意味です。課題で2種類のサイズを測るのは、この予想どおりになるかを確かめるためです。測る前に「こうなるはず」と書いておくと、結果との比較がそのまま考察になります。

      2

      課題1：リストに入れて、「ア」「カ」で始まる数を数える

      スライド「本日の課題」課題１
      1. 配布の名前ファイルを1行ずつ読み、ArrayList<String> に入れる（読み方は第9回のファイル読み込みと同じ）
      2. 拡張for文で1つずつ取り出し、先頭が「ア」なら、「カ」なら、それぞれ数を増やす

      先頭の文字を調べるには startsWith("ア") や charAt(0) が使えます。

      日本語のファイルを読むときは文字コードの指定が大切です。指定しないと文字化けして、1件も数えられないことがあります。読み込むときに StandardCharsets.UTF_8（ファイルがShift_JISなら Charset.forName("MS932")）を指定してください。

      「ア」で始まるかどうかは、ひらがなの「あ」や半角の「ｱ」とは別の文字として扱われます。データにそういう名前が混ざっていないか、最初に確かめておくと数え間違いを防げます。

      3

      検索時間を正しく測る

      スライド「本日の課題」検索時間を調べてまとめよ
      long start = System.nanoTime();
// ここに、測りたい検索の処理
long end = System.nanoTime();
System.out.println((end - start) + " ns");
      15300 ns                          ← 1回だけだとばらつくので、繰り返して平均する（手順3の表）
      気をつけること理由と対策
      1回だけ測らない1回の検索は短すぎて、ばらつきに埋もれる。同じ検索を1000回などまとめて繰り返し、合計を回数で割る
      最初の何回かは捨てるJavaは、動かし始めは遅く、繰り返すうちに最適化されて速くなる（JIT）。測る前に何回か空回しする
      表示の処理を入れないprintln は検索よりずっと遅いので、測る範囲の外に出す
      何度か測って並べる同じ条件で数回測り、平均やばらつきも表に入れる

      System.currentTimeMillis() はミリ秒単位なので、短い検索では0になってしまいます。ナノ秒単位の nanoTime() を使います。

      4

      課題1：3つの位置、2つのサイズで比べる

      スライド「本日の課題」先頭要素、最終要素、任意の要素

      検索は、名前を1つ渡して「あるか」を先頭から順に比べる処理です（contains でも、自分で書いたループでもかまいません。どちらを使ったかはレポートに書きます）。

      検索する名前予想（線形探索）
      先頭の要素1回比べるだけなので、いちばん速い
      最終の要素全部と比べるので、いちばん遅い。データが2倍なら約2倍
      任意（真ん中あたりなど）その位置に比例する

      「リストにない名前」も1つ測っておくと、最後まで比べてから「ない」とわかるので最終要素とほぼ同じ時間になる、という確認ができ、考察に使えます。

      5

      課題2：どんな木にするか決める

      スライド「木構造の例（50音でのindex）」「木構造の例（２分木のindex）」

      スライドには2つの例があります。どちらにするか（または別の形にするか）を決めることも、課題の一部です。

      形作り方考えどころ
      50音の索引根の下に「ア」「カ」「サ」…の行、その下に「ア」「イ」「ウ」…の段、その下にデータのリスト名前の多い行に偏る。スライドのとおり、多いところは2文字目も使ってバランスをとってよい
      二分木の索引スライドの TreeDic のように、各ノードが索引の文字、左右の子、データのリストを持つ深さをいくつにするか。1+2+4+8+16＝31、さらに+32＝63 なので、深さ5〜6で何文字ぶんの区切りが作れるか
      1文字ずつの木（配布サンプル）名前の1文字目、2文字目…を順にたどる。単語の終わりに目印のノードを置く同じ文字で始まる名前が多いと、途中まで共通の道を通る

      二分木は「左は小さい、右は大きい」の決まりで作ると、途中で一方だけを調べればよくなるので速くなります。ただし、名前を50音順のまま入れていくと、右へ右へと一直線の木になり、線形リストと同じ速さに戻ってしまいます。これがスライドの「バランスの良い木を作るのが難しい」の意味です。

      6

      配布サンプル（TreeMaking）を読む

      配布コード TreeNode／TreeNodeWithParent
      部分していること
      addNode(word)1文字目の子があればそこへ、なければ作って、残りの文字を再帰的に追加。文字がなくなったら終わりの目印（"E"）の子を付ける
      isFound(search)1文字目が合う子へ進み、残りの文字で再帰。最後まで進んで目印があれば「ある」。深さ優先探索の形
      TreeNodeWithParent親へのつながりを持たせ、今いるノードまでの文字列を表示できる版。どの順にノードを調べたかが出力でわかる
       
      true
Serch:nullフ
Serch:nullフシ
Serch:nullフシギ
Serch:nullフシギダ
Serch:nullフシギソ
Serch:nullフシギバ
Serch:nullフシギバナ
true

      2つ目の木（TreeNodeWithParent）は、調べたノードまでの文字列を表示します。「フシギバナ」を探すのに、先に「フシギダ」「フシギソ」の枝を見てから「フシギバ」に進んでいて、深さ優先探索で枝を順に試していることがわかります。先頭の null は、根のノードのキーが null なのを、そのまま文字列につないでいるためです（表示を直すなら、根を飛ばしてつなぎます）。

      終わりの目印を "E" という文字で表しているので、英字の「E」を含む名前を入れると目印と区別がつきません。カタカナだけのデータなら問題になりませんが、自分の木を作るときは、目印を別の方法（真偽値の変数など）で持つほうが安全です。

      7

      幅優先探索と深さ優先探索で探して、時間を測る

      スライド「探索の手立て」「幅優先探索」「深さ優先探索」

      スライドのとおり、2つの違いは「探索予定」の表に、展開したノードをどこへ入れるかだけです。第3回の迷路探索のOPENリストと同じ考え方です。

      方法展開した子の入れ場所Javaで使える入れ物
      幅優先探索探索予定の後ろに入れる（浅い段から順に調べる）ArrayDeque を待ち行列として（addLast／pollFirst）
      深さ優先探索探索予定の前に入れる（1本の枝を奥まで調べる）ArrayDeque をスタックとして（addFirst／pollFirst）、またはサンプルのような再帰

      測る名前は、課題1と同じもの（先頭・最終・任意）を使うと、リストと木を同じ表で比べられます。調べたノードの数も数えておくと、時間だけでは見えにくい違いが説明しやすくなります。

      1文字ずつの木では、正しい文字の子へ進めば答えが出るので、深さ優先が有利になりやすいです。一方、幅優先は浅い段をすべて調べてから下へ進むので、同じ木でも調べるノードの数が大きく変わります。どちらが速いかは木の形と探す名前によって変わるので、結果がそうなった理由を木の形から説明すると考察になります。

      8

      発展：ハッシュ、均衡木、最長しりとり

      スライド「発展課題」
      • ハッシュ：HashSet<String> に入れて contains で探すだけで O(1) の探索になります。課題1と同じ名前で時間を測り、データのサイズを変えても時間がほとんど変わらないかを確かめます。
      • バランスをとりながら木を作る：50音順に並べたリストの真ん中を根にし、左半分・右半分の真ん中をそれぞれの子にする、を繰り返すと、偏りのない二分木になります。入れるたびに形を直す方法（AVL木、赤黒木）を調べるのも一つです。Javaの TreeMap は赤黒木でできています。
      • 最長しりとり：名前を「頭の文字→お尻の文字」の矢印と考えると、同じ名前を2度使わずにたどれる最長の道を探す問題になります。全部の並べ方を試すと組み合わせが爆発するので、深さ優先探索で途中で打ち切る工夫が必要です。「ン」で終わる名前や、伸ばし棒（ー）・小さい文字（ャ、ュ）の扱いのルールも決めておきます。
      !

      うまくいかないとき

      症状原因と対処
      「ア」で始まる数が0になる／名前が文字化けする読み込みの文字コードがファイルと違う。UTF-8 か MS932（Shift_JIS）を指定する
      1件目だけ見つからないファイルの先頭に、目に見えない印（BOM）が付いている。1件目の先頭の文字を取り除く
      時間が毎回大きく違う／0になる1回だけ測っている、または currentTimeMillis を使っている。nanoTime で、繰り返して平均する
      先頭の要素がいちばん遅い最初に測ったものはJITの最適化前で遅い。測る前に空回しする
      StringIndexOutOfBoundsException空の文字列に substring(0,1) や charAt(0) をした。空行を読み飛ばす
      StackOverflowError再帰が深すぎる（一直線に偏った木など）。木の形を見直すか、再帰ではなくスタックを使う
